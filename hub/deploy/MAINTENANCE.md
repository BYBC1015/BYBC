# Hub 工程维护

用户要求：工程师每周至少维护一次，检查日志和用户问题，有明确问题时优化更新，保留实际验证证据。

## 两层执行

- 服务器 `codex-hub-maintenance.timer` 每小时做一次轻量检查，不调用模型。维护周以北京时间星期一 09:00 为起点。同项目同周只产生一项工程师任务；上周尚在执行时记录延续，避免重叠写入。
- 任务交给项目配置的真实工程师身份。绑定设备离线时保存任务和反馈，等执行器恢复。网页在线不等于执行器在线。
- 当前 Codex 对话的「Hub 每周维护督办」每周一 10:00 检查排队、执行、验证和备份情况。不重复创建同周任务；没有有意义的变化时不通知。

## 反馈闭环

聊天侧栏和项目页面提供「问题与建议」。用户可以直接报告 bug 或想法，保留复现步骤、期待结果和相关工作。
页面地址去掉查询参数与片段，自动记录可获取的页面端口、浏览器/视口、Hub 版本和关联任务。浏览器环境与实际执行电脑分别记录，不根据 User-Agent 猜测 BYBC 主机名。

工程师必须复现、定位、修复和回归后记录证据，才能标记已修复。排队、领取和生成一段答复都不等于修复。无法完成时说明原因与下一步；用户仍可重新报告或打开问题。

## 安装与检查

服务代码部署后，将本目录的 `.service` 和 `.timer` 安装到 `/etc/systemd/system/`，执行 `systemctl daemon-reload`，再 `systemctl enable --now codex-hub-maintenance.timer`。
部署第一次应手动运行一次服务，并验证产生的任务、实际工程师绑定和维护页。定时器每小时检查，同周不重复调用模型。

`codex-hub-maintenance.service` 仅操作示例部署项目 `private-server-buildout`。迁移时修改 `--project`，并在数据库配置实际工程师身份，禁止盲目复制数字身份 ID。

例行检查：

```sh
systemctl status codex-hub-maintenance.timer --no-pager
systemctl list-timers codex-hub-maintenance.timer --no-pager
journalctl -u codex-hub-maintenance.service -n 20 --no-pager
```

诊断文件 `/var/lib/codex-hub/maintenance-diagnostics.json` 仅含固定错误类别计数、HTTP 状态类别及健康检查，不存原始日志。它是每项服务最近最多 1000 条记录的样本，不能宣称覆盖一周所有请求；日志不可读时明确记录缺失。

回复速度检查使用有本项目读取权限的设备连接访问 `GET /api/projects/{slug}/execution-timings?limit=100`（上限 500 条）。分别检查发送到取得执行凭据、取得凭据到启动、启动到首条公开答复、执行总时长。状态心跳及“已开始处理”不能算作公开答复；记录只保存时间，不复制消息正文、推理或工具参数。首条答复记录在任务完成后仍保留。旧任务或部署中途才开始观测的任务标记为部分数据，不能据此宣称秒回；此接口也不测量浏览器最终绘制时间。

用量检查使用相同权限的 `GET /api/projects/{slug}/execution-usage?limit=100`（上限 500 条）。只统计执行器实际上报的输入、缓存输入和输出计数；缓存输入属于总输入的一部分，不能重复相加。缺失、无效或冲突计数明确记为未知，不用提示词字符数推算。执行开始时冻结的模型选择、实际执行设备与执行代次一同保留；选择记录本身不证明提供方实际路由，计数也不等于金额。旧客户端尚未上报计数时，不能宣传已经测得费用下降。

## 异常驱动的改进

每小时的同一维护入口还扫描最近 24 小时最多 200 次执行：同一设备和执行方式出现至少 3 个不同任务失败，或总控连续 3 个可完整测量的首次公开答复超过 120 秒，形成诊断证据。缺失、部分观测和时钟倒退不冒充慢回复；维护任务及同对话衍生工作不参与触发，防止维护检查自己形成循环。

扫描只读取本地记录，不调用模型。工程维护尚未领取时可以合并有限证据；已领取、执行或阻塞时仅保留新信号，不修改其工作说明。已有同类维护结果待核验时不重复发单；其他新的异常每天最多创建一项诊断，沿用项目真正的工程师与设备配置，并尊重关闭维护的设置。重复扫描、丢失回执和重试不能重发已处理证据。

工程师须核对原始需求与最新反馈，不自动重做失败的生产任务，也不得调整验收标准来掩盖问题。记录经验需区分“待验证”和“已有复现、修复、回归、发布/回滚证据”。应用由这些可核对的维护和经验逐步改进，不把模型自述当作已经完成升级。

## 回归与发布

针对修改运行相关测试。验证聊天附件、群聊、智能体身份、断线恢复与取消场景；记录版本、测试结果、仍未解决的问题和回滚位置。
代码备份只包含所需源码、依赖锁、部署示例、测试和发布记录，不包含环境密钥、登录凭据、数据库、用户附件或私有原始日志。真实上传位置以本轮发布记录为准。

维护任务自身不自动重放结果不明的生产任务。已开始工作的设备掉线时先核对执行收据与副作用，不凭另一个设备上线就重跑。
